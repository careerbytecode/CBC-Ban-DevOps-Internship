# SonarQube Cloud Account and Azure DevOps Integration

## What We Wanted to Do

FlavorForge uses SonarQube Cloud to perform automated source-code quality analysis as part of the Azure DevOps CI/CD pipeline.

The integration follows this flow:

```text
GitHub Repository
       |
       v
SonarQube Cloud
       |
       | Authentication Token
       v
Azure DevOps Service Connection
       |
       v
Azure DevOps Pipeline
       |
       v
SonarQube Cloud Analysis
       |
       v
Quality Gate
```

The purpose of this step was to:

- Sign in to SonarQube Cloud.
- Verify the SonarQube Cloud account and organization.
- Verify the FlavorForge project.
- Create an authentication token.
- Connect SonarQube Cloud with Azure DevOps.
- Verify the Azure DevOps service connection.
- Keep the authentication token outside the source repository.

# 4. Create the SonarQube Cloud Authentication Token

Azure DevOps requires authentication when communicating with SonarQube Cloud.

A personal authentication token was created in SonarQube Cloud for the Azure DevOps integration.

Open the SonarQube Cloud account security/token area.

The token page can be accessed from:

```text
Account
   |
   v
Security / Access Tokens
```

Create a new token using a descriptive name.

For example:

```text
flavorforge-azure-devops
```

The exact token name can be different as long as it clearly identifies its purpose.

---

# 5. Token Security

The authentication token is a secret credential.

It must **not** be:

- committed to GitHub
- written directly inside `azure-pipelines.yml`
- placed in `README.md`
- pasted into public documentation
- included in screenshots
- shared in chat messages
- stored as plain text in the repository

The correct approach is:

```text
SonarQube Cloud
       |
       | Generate token
       v
Azure DevOps Service Connection
       |
       | Securely stores credential
       v
Azure DevOps Pipeline
```

The token is used by the Azure DevOps service connection rather than being hard-coded into the pipeline YAML.

# 7. Important: Do Not Put the Token in the Pipeline YAML

The authentication token should not be written like this:

```yaml
SonarCloudToken: "my-real-token-value"
```

This would expose a credential in source control.

Instead, Azure DevOps stores the credential in the service connection.

The pipeline refers to the service connection by name.

Conceptually:

```text
Pipeline YAML
     |
     | service connection name
     v
Azure DevOps Service Connection
     |
     | securely stored token
     v
SonarQube Cloud
```

This keeps the authentication credential separate from the source code.

# 9. Configure the SonarQube Cloud Service Connection

Configure the service connection using the authentication token generated in SonarQube Cloud.

The connection should point Azure DevOps to the SonarQube Cloud organization.

The important configuration is conceptually:

```text
Service connection type:
SonarQube Cloud

Authentication:
Token

Token:
<secure SonarQube Cloud token>

Service connection name:
<the name used by the pipeline>
```

The actual token value should never be included in this documentation.

After entering the required information, use the **Verify** option.

If verification succeeds, save the service connection.

The service connection acts as the secure bridge between Azure DevOps and SonarQube Cloud.

The integration can be represented as:

```text
                    FlavorForge
                  GitHub Repository
                         |
                         v
                SonarQube Cloud
                         |
                  Authentication
                       Token
                         |
                         v
             Azure DevOps Service
                  Connection
                         |
                         v
              Azure DevOps Pipeline
                         |
                         v
                SonarQube Analysis
                         |
                         v
                  Quality Gate
```

The important point is that the pipeline does not need to contain the actual authentication token.

# 13. SonarQube Cloud in the Azure DevOps Pipeline

After the service connection has been created, the Azure DevOps pipeline can use SonarQube Cloud tasks.

The pipeline follows this general sequence:

```text
Prepare SonarQube Cloud Analysis
              |
              v
        Build Application
              |
              v
          Run Tests
              |
              v
      Run SonarQube Analysis
              |
              v
       Publish Quality Gate
```

The preparation task connects the pipeline configuration to the SonarQube Cloud project.

A typical configuration has the following structure:

```yaml
- task: SonarCloudPrepare@4
  displayName: "Prepare SonarCloud Analysis"
  inputs:
    SonarCloud: '<Azure DevOps service connection name>'
    organization: '<SonarQube Cloud organization>'
    scannerMode: 'cli'
    configMode: 'manual'
    cliProjectKey: '<SonarQube Cloud project key>'
    cliProjectName: 'FlavorForge'
```

The actual values used by FlavorForge should match the values configured in the repository's `azure-pipelines.yml`.

---

# 14. SonarQube Analysis

After the preparation step, the pipeline runs the SonarQube Cloud analysis.

The analysis evaluates the source code and produces code-quality information.

Conceptually:

```text
Source Code
     |
     v
SonarQube Cloud Scanner
     |
     +------------------+
     |                  |
     v                  v
Code Quality       Security Issues
     |
     v
Quality Gate
```

The pipeline then publishes the analysis result.

---

# 15. Quality Gate

The SonarQube Cloud Quality Gate provides a pass/fail quality decision for the analyzed project.

The overall pipeline flow becomes:

```text
GitHub
   |
   v
Azure DevOps Pipeline
   |
   v
Build
   |
   v
Test
   |
   v
SonarQube Cloud Analysis
   |
   v
Quality Gate
   |
   +---- PASS ----> Continue Pipeline
   |
   +---- FAIL ----> Stop / Handle Failure
```

This makes SonarQube Cloud part of the DevSecOps quality-control process.

---

# 16. Why We Used a Service Connection

Using an Azure DevOps service connection provides a cleaner separation between:

```text
Application Source Code
```

and:

```text
Authentication Credentials
```

Instead of putting a secret into the repository:

```text
azure-pipelines.yml
        |
        X
   hard-coded token
```

the secure design is:

```text
azure-pipelines.yml
        |
        | references service connection
        v
Azure DevOps Service Connection
        |
        | securely stores authentication
        v
SonarQube Cloud
```

This is the preferred approach for CI/CD authentication.
